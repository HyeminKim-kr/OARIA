# 청킹 전략 선택 근거: Parent-Child vs 동적 확장

> **목적**: 우리가 순수 Parent-Child 대신 "동적 확장(On-the-fly Parent)" 방식을 선택한 이유 설명
>
> **작성일**: 2025-12-23
>
> **결론**: 같은 목표를 더 단순한 구조로 달성

---

## TL;DR

| 구분 | Parent-Child | 우리 방식 (동적 확장) |
|------|-------------|---------------------|
| **본질** | 저장/인덱스 구조 선택 | 검색/생성 파이프라인 설계 |
| **Parent 저장** | DB에 별도 저장 | 저장 X, S3에서 런타임 조립 |
| **관계 관리** | child ↔ parent 링크 필요 | offset만으로 계산 |
| **효과** | 검색↔생성 분리 | 동일 |
| **복잡도** | 높음 | 낮음 |

> **핵심**: Parent-Child의 '효과'만 가져오고 '구조 비용'은 피하는 타협안

---

## 1. Parent-Child 전략의 본질

Parent-Child 전략은 **"두 개의 인덱스(또는 두 레벨 데이터)"를 운영하는 전략**이다.

```
┌─────────────────────────────────────────────────────────────┐
│  Parent-Child 구조                                           │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  ┌─────────────────────────────────────┐                    │
│  │  Parent 청크 (2000 토큰)              │  ← DB에 저장       │
│  │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐   │                    │
│  │  │Child│ │Child│ │Child│ │Child│   │  ← DB에 저장       │
│  │  │ 1   │ │ 2   │ │ 3   │ │ 4   │   │     + 임베딩       │
│  │  └──┬──┘ └──┬──┘ └──┬──┘ └──┬──┘   │                    │
│  │     └───────┴───────┴───────┘       │                    │
│  │              parent_id 링크          │                    │
│  └─────────────────────────────────────┘                    │
│                                                              │
│  검색: child로 정밀 매칭                                      │
│  생성: parent 텍스트를 LLM에 제공                             │
└─────────────────────────────────────────────────────────────┘
```

### 필요한 것들
- parent 청크 저장 (벡터화 여부 선택)
- child 청크 저장 + 임베딩
- child ↔ parent 관계 관리
- 버전 변경 시 양쪽 일괄 재생성

## 2. 우리 시스템에서 Parent-Child가 멀어진 이유

### 2.1 이미 갖고 있는 구조

```
┌─────────────────────────────────────────────────────────────┐
│  우리 시스템 구조                                            │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  S3 (Canonical Text)          Weaviate (Chunks)             │
│  ┌─────────────────┐          ┌─────────────────┐           │
│  │ 논문 전문         │          │ child 청크       │           │
│  │ (원본 그대로)     │  ←────── │ + offset_start  │           │
│  │                  │  offset  │ + offset_end    │           │
│  │                  │  참조    │ + text_version  │           │
│  └─────────────────┘          └─────────────────┘           │
│         ↑                                                    │
│         │                                                    │
│    답변 시 필요한 범위만 잘라서 가져옴                          │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

우리는 이미:
- **원문을 S3에 canonical로 저장**하고
- **청크는 Weaviate에 offset으로만 참조**하고
- **답변 때 필요한 컨텍스트는 S3에서 잘라서 가져오는** 구조

→ 이 구조에서 **"parent 텍스트를 별도로 저장"하는 이득이 줄어듦**

### 2.2 Parent의 역할을 이미 S3가 하고 있음

| Parent-Child에서 Parent 역할 | 우리 시스템에서 대체 |
|----------------------------|-------------------|
| 넓은 컨텍스트 제공 | S3 canonical에서 offset 확장 |
| 답변 생성용 텍스트 | S3에서 런타임 조립 |
| child 관계 관리 | offset 계산으로 대체 |

→ **parent를 DB에 미리 만들어 저장하는 가치가 상대적으로 낮아짐**

## 3. 우리 방식: 동적 확장 (On-the-fly Parent)

### 3.1 개념

```
┌─────────────────────────────────────────────────────────────┐
│  동적 확장 (On-the-fly Parent)                               │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  [검색 단계]                                                  │
│  Weaviate에서 child 청크 검색 (600-800 토큰)                 │
│         ↓                                                    │
│  검색 결과: offset_start=12340, offset_end=13280             │
│         ↓                                                    │
│  [생성 단계]                                                  │
│  S3에서 확장 범위 계산:                                       │
│    parent_start = offset_start - 500                        │
│    parent_end = offset_end + 500                            │
│    (단, 섹션 경계 내에서만)                                    │
│         ↓                                                    │
│  확장된 컨텍스트를 LLM에 제공                                  │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 Parent-Child와 비교

| 항목 | Parent-Child | 동적 확장 |
|------|-------------|----------|
| **검색 정밀도** | child로 확보 | child로 확보 (동일) |
| **답변 컨텍스트** | parent에서 가져옴 | S3에서 런타임 확장 (동일 효과) |
| **Parent 저장** | 필요 | 불필요 |
| **저장량** | 2배 | 1배 |
| **관계 관리** | child-parent 링크 | offset 계산만 |
| **확장 범위 변경** | 재인덱싱 필요 | 런타임 조정 가능 |

### 3.3 핵심 차이

```
Parent-Child:
  "청킹을 2레벨로 설계하고, 그 둘을 조인/링크해서 쓰는" 구조

동적 확장:
  "청킹은 1레벨, 필요할 때 원문에서 확장하는" 파이프라인
```

> **같은 목표를 더 단순한 구조로 달성할 수 있어서, Parent-Child에서 멀어짐**

## 4. Parent-Child를 정식 채택하면 생기는 추가 의사결정

### 4.1 Parent를 저장할지?

| 선택 | 결과 |
|------|------|
| 저장함 | 스토리지 증가, 인덱싱/관리 증가 |
| 저장 안함 | 결국 S3에서 잘라야 함 → "굳이 Parent-Child라 부를 필요가?" |

### 4.2 Parent도 벡터화할지?

| 선택 | 결과 |
|------|------|
| 벡터화함 | 멀티-레벨 검색 가능, 비용 큼 |
| 벡터화 안함 | parent는 "조회용 컨테이너" → S3와 역할 겹침 |

### 4.3 링크(관계) 관리

- child에 `parent_id`, `parent_span` 등 관리 필요
- `textVersion`/청킹 버전 바뀔 때 일괄 재생성/정합성 필요
- **500만 논문 규모에서 이 운영 복잡도가 크게 다가옴**

---

## 5. 언제 Parent-Child가 다시 가까워질 수 있나?

### 5.1 S3 읽기 비용/지연이 너무 커질 때

```
현재: 검색 hit → S3에서 확장 컨텍스트 조립

문제 발생 시:
- S3 읽기 P95 latency가 튀거나
- 비용이 너무 커지면

해결책:
- parent 텍스트(또는 parent 범위 캐시)를 DB/캐시에 "미리" 저장
- 이 순간 Parent-Child가 가까워짐
```

### 5.2 "Parent 단위로 보여주는 UI"가 제품 핵심이 될 때

```
예시:
- 논문 뷰어에서 "이 근거가 속한 문단 전체"를 항상 보여주고
- 문단 단위로 탐색/인용이 중심이 되면

→ 문단(=parent)을 1차 객체로 두는 게 더 자연스러워짐
```

### 5.3 Reranker/LLM 컨텍스트 비용이 너무 커질 때

```
현재: 동적 확장으로 컨텍스트 크기가 가변적

문제 발생 시:
- 검색 결과가 많아질수록 확장 컨텍스트가 커져
- LLM 토큰 비용이 예측 불가능하게 증가

해결책:
- parent를 일정 크기로 고정해서 컨텍스트 안정화
- 이 순간 Parent-Child가 가까워짐
```

## 6. 최종 정리

### 우리가 선택한 방식

```
섹션 기반 + Recursive (600-800 토큰, overlap)
    + Prefix (컨텍스트 힌트: [TITLE][SECTION][TEXT])
    + 검색 후 주변 확장 (작은→큰)
```

### Parent-Child와의 관계

| 구분 | 설명 |
|------|------|
| **닮은 점** | 검색은 작게, 생성은 크게 (동일한 목표) |
| **다른 점** | Parent를 저장하지 않음 (구조 비용 회피) |
| **본질** | Parent-Child가 아니라 "On-the-fly Parent (동적 확장)" |

### 선택 이유

1. **저장량 최소화**: 500만 논문 규모에서 2배 저장은 부담
2. **운영 복잡도 감소**: parent-child 관계 관리 불필요
3. **유연성 확보**: 확장 범위를 런타임에 조정 가능
4. **기존 구조 활용**: S3 canonical이 이미 parent 역할 수행
5. **offset 재현 유지**: 핵심 요구사항과 충돌 없음

> **결론**: Parent-Child의 '효과'는 그대로 가져가면서, '구조 비용'은 피하는 실용적 타협안
