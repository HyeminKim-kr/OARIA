> **Category**: batch

## Context (배경)

### 문제점

기존 Fire-and-forget 방식의 Celery 태스크 구조:
- 워커 재시작 시 진행 중인 작업 손실
- "processing" 상태에서 stuck되면 수동 개입 필요
- 재시작 메커니즘 없음
- Redis를 사용하면서도 활용하지 않음

### 해결 방향

Redis 기반 robust한 작업 관리 시스템:
- 상태 머신 기반 작업 관리
- Celery Beat로 주기적 dispatch 및 복구
- 분산 락으로 중복 실행 방지
- Heartbeat 기반 stuck 작업 감지

## API 변경

### User Backend (FastAPI)

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `/lab/sample-embed/trigger` | POST | 작업 생성 (Redis 큐에 등록) |
| `/lab/sample-embed/{id}/status` | GET | 실시간 상태 조회 (Redis) |
| `/lab/sample-embed/{id}/retry` | POST | 작업 재시도 |
| `/lab/sample-embed/{id}/cancel` | POST | 작업 취소 |

### Admin Backend (NestJS)

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `/sample-embeddings/{id}/status` | GET | 실시간 상태 프록시 |
| `/sample-embeddings/{id}/retry` | POST | 재시도 프록시 |
| `/sample-embeddings/{id}/cancel` | POST | 취소 프록시 |

## Notes

- Redis가 source of truth가 아님 (DB가 최종)
- Redis 장애 시 DB에서 복구 가능 (sync_jobs_from_db 태스크)
- 최대 재시도 횟수: 3회
- Heartbeat 타임아웃: 120초 (2분)
- 기존 run_sample_embed 태스크는 하위 호환성 유지
