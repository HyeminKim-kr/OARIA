# Reranker 비동기 처리 개선 + 타임아웃/성능 최적화

> **Category**: backend
> **Date**: 2026-01-30
> **Status**: completed

---

## Context (배경)
- Reranker 모델(`CrossEncoder.predict()`)이 동기 호출로 FastAPI 이벤트 루프를 블로킹
- CPU 기반 추론 시 100~500ms 동안 다른 모든 요청이 대기 상태
- Admin backend의 lab search 타임아웃(60초)이 reranker 처리 시간(~63초)보다 짧아 타임아웃 발생
- 같은 코드베이스의 `weaviate_service`, `s3_service`는 이미 `asyncio.to_thread()`를 사용하는 패턴

## Solution (해결 방안)

### 1단계: 이벤트 루프 블로킹 해소
- [x] `reranker_service.rerank()` 호출을 `asyncio.to_thread()`로 래핑
- [x] 3곳(rag_service, paper_rag_service, lab router) 모두 적용

### 2단계: 타임아웃 여유 확보 + 처리량 감소
- [x] Admin backend Lab module 타임아웃: 60초 → 120초
- [x] Admin backend Lab service search 타임아웃: 60초 → 120초
- [x] Reranker 처리 문서 수 감소: rag_service 20 → 10, paper_rag_service 15 → 10

## Changes (변경 사항)
### 수정된 파일
- `backend/app/services/rag_service.py` - `asyncio.to_thread()` 래핑, `rerank_top_k` 20→10
- `backend/app/services/paper_rag_service.py` - `import asyncio` 추가, `asyncio.to_thread()` 래핑, `rerank_top_k` 15→10
- `backend/app/routers/lab.py` - `import asyncio` 추가, `asyncio.to_thread()` 래핑
- `admin/backend/src/modules/lab/lab.module.ts` - HttpModule timeout 60000→120000
- `admin/backend/src/modules/lab/lab.service.ts` - search 요청 timeout 60000→120000

## Notes
- `asyncio.to_thread()`는 기본 ThreadPoolExecutor에서 실행되어 이벤트 루프 블로킹 해소
- PyTorch 추론은 C 확장에서 GIL을 해제하므로 스레드 기반 병렬 처리 효과적
- Study agent는 동일한 rag_service/paper_rag_service를 사용하므로 자동으로 혜택 받음
- Study agent는 SSE 스트리밍 방식이라 HTTP 타임아웃 이슈 없음 (유저 프론트엔드 axios 타임아웃 미설정 = 무제한)
