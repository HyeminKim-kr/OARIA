# Batch 임베딩 에러 처리 개선 (429 Rate Limit & No Sections)

> **Category**: batch
> **Date**: 2026-01-15
> **Status**: completed

---

## Context (배경)

임베딩 작업에서 다음 에러들이 발생:

### 1. 429 TPM Rate Limit (9건)
- OpenAI text-embedding-3-small 모델
- 조직 TPM 한도: 1,000,000 tokens/min
- 현재: 재시도 로직 없이 바로 실패 처리

### 2. No sections found (1건)
- `pmc:PMC12764464`: 섹션 추출 실패
- 현재: 다른 에러와 동일하게 `failed` 처리 → 의미 없는 재시도 대상

## Solution (해결 방안)

### 1. OpenAI 임베딩 클라이언트 재시도 로직
- 지수 백오프 + 지터
- Retry-After 헤더 우선 사용
- 최소 대기 시간 250ms (버스트 완화)
- 최대 재시도 5회

### 2. Token Budget 쓰로틀링
- 분당 토큰 사용량 추적 (슬라이딩 윈도우)
- API 호출 전 토큰 수 추정 (약 4자당 1토큰)
- 한도 근접 시 자동 대기

### 3. 에러 분류 시스템
- `RETRYABLE`: 429, 5xx, 네트워크 오류
- `TERMINAL`: No sections, No fulltext, No chunks, 파싱 실패
- `UNKNOWN`: 기타 (안전하게 재시도 시도)

### 4. "No sections found" 분리
- `[TERMINAL:type]` 프리픽스로 에러 타입 구분
- `run_reembed()`에서 TERMINAL 에러 제외

## Notes

- 기존 `collectors/rate_limiter.py`는 PMC API 전용으로 유지
- 임베딩용 `embedding/rate_limiter.py` 별도 구현
- DB 스키마 변경 없음 (기존 `embedding_error` 컬럼 활용)
- 토큰 예산은 AsyncEmbeddingClient에만 적용 (sync는 단일 요청이므로 불필요)

## 재시도 로직 상세

```python
# 백오프 계산
base = min(0.5 * (2 ** attempt), 30.0)  # 0.5s → 1s → 2s → ... → 30s
base = max(base, retry_after_ms / 1000)  # API 권장 시간 우선
base = max(base, 0.25)                   # 최소 250ms
jitter = random.uniform(0, 0.2 * base)   # 0~20% 지터
delay = base + jitter
```

## 재시도 제외 대상 (TERMINAL 에러)

| 에러 타입 | 설명 | 처리 |
|-----------|------|------|
| `no_sections` | 섹션 추출 실패 | 수집 파이프라인 재검토 필요 |
| `no_fulltext` | 본문 없음 | S3 저장 문제 확인 |
| `no_chunks` | 청크 생성 실패 | 청커 설정 확인 |
| `bad_request` | 잘못된 요청 (400) | 입력 데이터 확인 |
| `auth_error` | 인증 실패 (401/403) | API 키 확인 |
