# Database 문서화 및 Auth 스키마 설계

> **Category**: database
> **Date**: 2025-12-31
> **Status**: completed

---

## Context (배경/근거)

### 문제 1: DB 문서 부재
- 데이터베이스 테이블 스키마에 대한 통합 문서가 없음
- 기존 스키마는 `infra/init/*.sql`, `alembic/versions/*.py`, 스파이크 문서에 분산

### 문제 2: Auth 스키마 단순함
- 기존 `users` 테이블이 너무 단순
- `is_superuser` 플래그 하나로 관리자/사용자 구분 → 확장성 부족
- `google_id` 직접 저장 → 다른 소셜 로그인 추가 시 컬럼 증가
- JWT refresh token 관리 체계 없음

### 요구사항
- 관심사별 테이블 문서 분리 (papers, users, batch)
- 유저/어드민 테이블 분리
- 소셜 로그인 확장 가능 구조
- JWT refresh token 관리 (양쪽 백엔드 모두)

---

## Solution (해결 방안)

### 접근 방식

1. **문서 구조화**: `docs/database/` 폴더 생성, 관심사별 분리
2. **Auth 스키마 재설계**: 5개 테이블로 분리
   - `users` - 서비스 사용자 (소셜 로그인 전용)
   - `admin_users` - 관리자 (이메일/비밀번호, role 기반)
   - `social_accounts` - 소셜 로그인 연동 (1:N)
   - `user_refresh_tokens` - 사용자 JWT refresh
   - `admin_refresh_tokens` - 관리자 JWT refresh

## Notes (추가 노트)

### 구현 필요 사항
- `users.md`의 새 스키마는 **설계 문서 상태**
- 실제 구현 시 Alembic 마이그레이션 필요:
  1. `social_accounts` 테이블 생성
  2. 기존 `users.google_id` 데이터 이전
  3. `users`에서 `google_id`, `is_superuser` 컬럼 제거
  4. `admin_users`, `*_refresh_tokens` 테이블 생성

### 보안 고려사항
- Refresh token은 SHA256 해시만 DB 저장
- Token rotation 지원 (revoked_at 컬럼)
- 비밀번호는 bcrypt (cost 12+)
